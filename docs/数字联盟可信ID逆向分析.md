# 数字联盟（Shuzilm）可信 ID 逆向分析：从 libdu.so 到构造签发

> **声明：本文由 AI（ZCode / GLM）辅助完成全部分析、实验与撰写**，人工负责方向确认与结果复核。文中所有结论均有可复现的实验或字节级证据支撑。

## 1. 背景

知乎 Android 客户端内嵌数字联盟「可信 ID」SDK（`libdu.so`，v8.4.0）。SDK 采集设备指纹上报服务端，换取一个设备标识 `ms_id`，此后每次请求通过 `x-ms-id` 头携带，供业务侧风控使用。本文还原其完整签发协议，并给出纯 Python 的请求构造实现，最终签发的 ID 通过了知乎真实接口的校验。

样本与工具：

| 项 | 内容 |
|---|---|
| 样本 | `libdu.so` v8.4.0（arm64，取自知乎 11.10.0） |
| 静态分析 | IDA Pro + 自写解密脚本 |
| 动态环境 | unidbg（JDK21）、MuMu 模拟器、reqable 抓包 |
| 复现实现 | Python 3（`shuzilm_protocol.py` / `shuzilm_forge.py` / `checkid.py`） |

## 2. 字符串解密

so 内所有敏感字符串（端点路径、字段名、盐值）以 blob 形式内嵌 `.text`，4 字节对齐，由 `sub_717C0` 运行时解密：

```
plain[k] = (enc[2k+1] - 1) ^ k      判尾：enc[2k+1] == 0
```

注意：偶数位是填充数据，不能用 `data[off]==0` 过滤，否则漏解大半。穷举全库共解出 **11272 条**唯一字符串，端点路径、字段名、盐值全部来自这里。

## 3. 传输协议

- 通道：`POST https://auni.telecome.cn/a/d2api/report?v=8.1&t=a&e=2`（主通道，签发 ID）；另有 adt/mdna/dcc2 等 11 个端点。
- 传输层：**每端点独立 XOR 秘钥（`sub_847F0` 选取，`sub_4FF88` 逐字节循环异或）+ zlib 压缩**，请求/响应同钥。AES-ECB 只用于补充 ID 的本地落盘，与传输无关。
- URL 参数（端点 6 专属）：

| 参数 | 值 |
|---|---|
| `p` | `md5(包名 + ".37be8a1e.v8.4.0")`，App 标识 |
| `r` | UUID 去横杠 |
| `n` / `l` | 请求计数器（全局变量 C1934/C1938） |
| `h` | `md5(n_a + ".889e0b01")`，首装无会话时为字面量 `"0"` |

## 4. 请求体结构

d2api 请求体为紧凑 JSON：**顶层 28 键 + `vB2` 嵌套对象承载整块指纹（144 键）**。`vB2` 嵌套是签发硬条件——指纹块缺失时服务端只回裸 `{"err":"0"}`。

指纹块内容：

- `rG0..rG15`：`android.os.Build` 的 22 个 String 静态字段（SERIAL/BOARD/…/SOC_MODEL），键名由 `snprintf("rG%x", i)` 生成；slot0 仅 API≤28、slot18-21 仅 API≥31 才采集。附加键 `Kvr`=radio 版本、`fKe`=SUPPORTED_ABIS 逗号拼接、`tNP`=序列号。
- `R*`：系统属性族（构建描述、指纹、基带、运营商、时区、序列号等数十项）。
- 环境：boot_id UUID、APK 安装路径、本机 IP 列表、GPS 坐标、MAC、电池、屏幕等。
- 设备签名：`sKZ`/`P1J` = `sha1(WLAN MAC)` 摘要十六进制串切片 `d[1:7]:d[13:19]:d[7:13]` **三组全大写**冒号拼接；服务端在响应 `o_a` 中原样回显，可逐字节验证。
- 进程指纹：`K5f` = `upper(md5("%s%d%d%d" % (会话串, pid, rand, tid)))`。

**字符串混淆**：上述字符串值 put 前均经编码器 `sub_543EC`：

```
shift = (C1944 % 100) % 57 + 1        逐字符 c += shift，>0x7E 减 95（95 字符循环）
case  = (C1944 / 100) % 4 → 四种位置置换（已全部还原，n=2..93 全量对拍 0 失配）
```

状态字 `C1944` 来自服务端下发的点分串解析；环境为空时取 0（shift=1/case0）。**注意区分**：指纹/UUID/路径/IP/GPS/位标志等经编码器，时间戳、MAC、md5、统计 CSV 为裸值——搞混哪个键编码哪个键裸，是服务端 500 的直接原因。

## 5. 响应与落盘

响应关键字段：`err`（门控）、`nctl`（`"1"`→ID 在 `ocdd`，`"2"`→ID 在 `cdd`）、`n_a`（会话值，下次请求经 `h` 绑定）、`o_a`（票据回显）。ms_id 形态为 `DU + 34 位字母数字 + base64(前缀+"shu")`，共 88 字符。

SDK 将其写入 `/data/data/<pkg>/shared_prefs/<pkg>_dna.xml`：`device_id = base64( md5(sid[:64]) + sid )`，提取时 `base64 解码后取 [32:]`。

## 6. 服务端行为模型（实测）

| 实验请求 | 结果 |
|---|---|
| 同一设备身份重复上报 | 返回同一 ms_id（索引命中，不重新签发） |
| 仅改 App 标识 `p` | 仍返回同一 ms_id（索引键是设备不是 App） |
| 更换设备身份（指纹/MAC/boot_id 等全部换新） | 签发全新 ms_id |

结论：**服务端按设备稳定标识索引设备记录——命中回发原 ID，未命中签发新 ID**。同一公网 IP 下的不同设备各得各的 ID，不存在"按 IP 去重"或"固定签发"。

## 7. Python 构造签发

`shuzilm_forge.py`：不依赖捕获报文，逐键构造三个端点的请求体（键集与真实报文对拍零差异），随机生成全新设备档（品牌族 × 模型/指纹 + MAC×2 + android_id + boot_id + 序列号 + GPS + IP），指纹值按第二节编码器混淆后上报：

```
随机设备: OPPO PDM83  api=34
  MAC1=72:94:7c:78:4c:dc  android_id=492289f7ff77d01d
→ adt(5)  200  取会话 UUID
→ d2api(6) 200  签发全新 ms_id
→ mdna(16) 200
```

实测每次运行均得到历史记录中不存在的全新 ms_id，可无限签发。

## 8. 校验：checkid

`checkid.py` 把候选 `ms_id` 填入 `x-ms-id` 头，重放一条抓包请求：

```bash
python checkid.py
curl "http://127.0.0.1:5000/checkid?ms_id=<待验证ID>"
```

抓包后把 URL 与请求头填入 `checkid.py` 的空占位即可；会话头约 5 天过期，过期后连原 ID 也会 403，重新抓包填入。

实测（2026-10-07）：

| 输入 ms_id | 结果 |
|---|---|
| 抓包原 ID | 200 |
| Python 构造签发 ID ×2 | **200** |
| 拼凑垃圾 ID | 403 |

## 9. 小结

- 可信 ID = 服务端签发，端侧无本地算法；但签发协议（编码、混淆、嵌套结构）可完整还原并在 Python 中重建。
- 服务端按设备身份索引：同一身份复用旧 ID，全新身份签发新 ID，可稳定批量获取。
- 构造签发的难点不在加密强度，而在**逐键还原报文的编码性与取值格式**——任何一键的编码/裸值属性搞错都会被服务端拒绝。
