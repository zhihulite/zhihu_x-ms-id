# 数字联盟可信 ID 逆向 · 探索记录

> **声明：本文由 AI（ZCode / GLM）记录整理**，是《数字联盟可信ID逆向分析》的配套篇，按时间线还原整个探索过程——包括三次误判及其推翻过程。技术细节以正文文档为准，本文只记"怎么走到这一步的"。

## 起点

前期工作已完成：`libdu.so` v8.4.0 的字符串解密、22 槽 Build 指纹链、编码器四置换还原，unidbg 把整个 so 跑起来并打通了 adt/d2api/mdna 三端点真实往返，拿到了第一个 ms_id `DU2ovjZ1...`；纯 Python 重放脚本也能拿到同一 ID。

问题恰好出在这里：**无论 unidbg、Python 重放还是旧模拟器真机，拿到的永远是同一个 `DU2ovjZ1...`。**

## 阶段一：错误结论"服务端固定签发"

最初的全随机化实验（换 Build、换 MAC、换 boot_id）后 ID 依然不变；又试了改 URL 的 `p` 参数（App 标识），ID 还是不变。于是得出结论："该后端对任何设备都返回写死的固定 ID"，并写进了文档。

**这个结论是错的，而且错得很隐蔽**——它当时能解释所有观察，直到出现反例。

## 阶段二：一台新模拟器推翻了它

用户质疑结论，部署了一台全新模拟器（7555 端口，Xiaomi cupid 档案）实测：装知乎 → adb 点掉隐私弹窗同意 → SDK 上报 → 读 `dna.xml`。

```
新设备 ms_id = DUk8KSE2EIMCLk4O5K-DlYvRSefnPTwWIG1c...（全新）
```

ID 变了。"固定签发"被直接证伪。

回查根因：unidbg 仿真的 `ANDROID_ID = a543208bbf9cf92a`，**本来就是当初从旧 MuMu 上抄来的**——所以 unidbg、旧 MuMu、Python 重放三者提交的是同一份设备身份，命中了服务端同一条设备记录，当然返回同一个 ID。改 `p` 无效是因为索引键是设备不是 App。

进一步做 unidbg 全随机化（`-Ddu.randdev=true`，OnePlus/Google 两台虚拟设备）→ 两个全新 ID。服务端模型定案：**按设备稳定标识索引，命中回发原 ID，未命中签发新 ID**。

一个有意思的细节：unidbg 随机化没有传导到全部采集源（`R1e` 里仍是旧 android_id），但服务端照样签了新 ID——说明索引键也不是 android_id 单字段，更像 boot_id/指纹块/设备哈希的组合。构造时全换新即可全覆盖。

## 阶段三：500 之谜与第二个误判

Python 层尝试改指纹值重新组包 → 服务端 500。当时的结论写的是："JSON 重序列化改变字节表示，服务端要求字节级保真"——于是 Python 只能重放原始字节。

**这又是一条错结论。** 对照实验：把捕获的模板 JSON 解析后重序列化（不改任何值）再发——200，正常签发。服务端根本不在乎键序和字节表示。

真正的 500 原因有两个：
1. 报文里**哪些键经过编码器混淆、哪些是裸值**没搞清——把明文塞进编码位，服务端解码出垃圾；
2. 编码器 case0 置换的奇数长度实现有 bug（此前靠 unidbg 直接调用置换函数全量对拍修掉，368 组 0 失配）。

## 阶段四：逐键构造（forge）

把捕获报文的 210 个键逐键解剖：类型、取值格式、编码性（用解码器回读——解出干净语义值的是编码键如 UUID/路径/IP/GPS/位标志，解出垃圾的是裸值如时间戳/MAC/md5）。然后随机生成设备档，全部值从零生成，按真实编码器混淆，键集与真实报文对拍零差异后才联网。

```
第 1 发：HONOR HON-821 → ms_id = DU7gEeve...（全新）
第 2 发：OPPO PFM78   → ms_id = DUGYDh1x...（全新）
```

"字节级保真"论正式出殡。

## 阶段五：checkid 校验

用户提供了当日真机抓包（知乎搜索接口 `search_v3`，完整请求头）。写入 Python 后起本地校验服务，把候选 ID 填进 `x-ms-id` 头转发知乎：

| 输入 | 结果 |
|---|---|
| 抓包原 ID | 200（会话存活） |
| forge ID #1 / #2 | **200 / 200** |
| 垃圾 ID | 403 |
| 缺参 | 400 |

Python 全构造签发的 ID 被知乎真实接口接受——闭环完成。

## 误判清单

| # | 误判 | 推翻方式 |
|---|---|---|
| 1 | 服务端固定签发，任何设备同一 ID | 新模拟器实测拿到新 ID |
| 2 | JSON 重序列化→500，必须字节级保真 | 不改值重序列化实测 200；真因是编码性错标+置换 bug |
| 3 | sKZ 用 md5、仅第三组大写 | 第二台设备的服务端回显证明是 sha1 且三组全大写 |
| 4 | （工具）MSYS 路径传给 `-Dexec.args` | `mumu_props.txt` 静默不加载，so 直接返回 null 无上报 |

## 教训

- **服务端行为结论必须跨设备对照实测**，单变量测试（只改 p）容易得出"写死"的假象——你以为是随机化的变量可能根本没传导到采集源。
- **报文还原要逐键判定编码性**，不能整层假设"全都编码"或"全都不编码"。
- 质疑是有效的：误判 #1 正是被用户一句"我怀疑你的结论错误"部署新设备实测推翻的。AI 产出同样需要被验证，包括 AI 自己的结论。
